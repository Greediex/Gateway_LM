# Paper fidelity audit: Gateway LM pilot

Scope/version note: this audit describes the original `core.py`/`run.py` v1/v2 baseline. The separate `gateway_pilot/graph_v3` implementation added afterwards is documented in `GRAPH_V3_PROTOCOL.md` and `../GRAPH_V3_RESULT_VI.md`; historical findings below are preserved.

Checked 2026-11-07 by source inspection only. No pilot code/data/results changed; no benchmark, inference, installation, tuning or clone performed for this audit. Paths below are relative to the repository root.

## Finding

The current implementation is a custom, lightweight **joint lexical BM25 + workflow evidence expansion + exact-port DFS prerequisite closure** baseline. It implements useful parts of the Gateway design, but it is **not an integrated implementation or faithful reproduction of GoS, SkillDAG, SE-GoS, GraSP or the complete supplied HTML**. Cloning author repositories and pinning commits makes their code available for inspection; `gateway_pilot/core.py` and `gateway_pilot/run.py` contain no imports or calls into those repositories. There is no evidence here that the graph is optimized to the papers' protocols or the actual Edge hardware.

## Dependency direction is not interchangeable

The pinned GoS constructor explicitly creates `producer -> consumer` dependency edges from output/input overlap (`third_party/graph-of-skills/gos/core/engine.py:2027-2048`). Its retrieval kernel adds type-dependent reverse traversal weights, which allow a retrieved consumer to recover producers. Conversely, SkillDAG `depends_on` uses `consumer -> prerequisite`: `get_dependencies` (`graph.py:770`) and `expand_set` (`:829`) follow outgoing edges to dependencies. Copying the same source/target pairs across these formats without a semantic adapter would reverse their meaning.

The pilot has no such edge import. It indexes each Function's output-port string to producers and recursively visits a producer before appending the consuming Function (`core.py:64-101`). That is a coherent local direction convention, but only exact named-port compatibility. It does not validate a general JSON-Schema/subtyping/provenance-compatible port graph. Also, an upstream soft composition or similarity edge must not automatically become a mandatory execution dependency.

## Is the complete HTML implemented?

No. The inspected registry has **8 Skills and 16 Function records**, versus the supplied HTML's design inventory of 22 Skills, 101 use cases/workflows and 270 requirement items. The latter are requirements, not a callable API count. The pilot covers four initial diagnostic workflow families plus Internet/write-denial test paths, using synthetic replay adapters (`core.py:205`). It has local state/evidence validity, read-only capability checks and evidence-supported terminal validation.

The inspected runtime explicitly has no router/ubus/UCI/cloud/write executor. It does not implement firmware capability probing, full manifests and semantic schema compatibility, production auth/ACL, transactions/locks/rollback, persistent resumable jobs, scheduling/events, monitoring/forecast models, model/firmware lifecycle, Cloud/Fleet connectors or complete product observability. `graph_batch` pre-acquires a fixed workflow evidence bundle in Core; its model-success score measures evidence analysis with Core orchestration, not autonomous dynamic planning.

## Interpretation and next fidelity milestone

A paper's ALFWorld/SkillsBench/AppWorld success rate cannot be compared directly with this pilot's synthetic end-to-end diagnostic success: environments, models, skill libraries, prompts, budgets, verifiers and denominators differ. Current results describe the tested baseline and deterministic guards, not the best possible graph method or an intrinsic ceiling for all models below 3B.

A defensible next milestone is a separately versioned, development-only comparison of current closure against an actual pinned GoS adapter and a typed invocation-DAG implementation. Define edge semantics and producer alternatives first, preserve identical candidate/context/resource budgets, and score retrieval completeness, prerequisite validity, raw model quality, Core interventions, end-to-end outcomes and resource cost separately. Only introduce trace-driven evolution with train-only traces and an untouched held-out evaluation. These are recommendations, not work performed in this audit.
